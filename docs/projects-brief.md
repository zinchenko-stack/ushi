# Ushi — Проекты: дизайн-бриф

Документ описывает введение «Проектов» в Ushi: концепцию, модель данных, UI, поведение, архитектуру и фазы реализации. Цель — прийти к согласованному плану до того, как трогать код.

---

## 0. Параллельная разработка — важно

Текущее приложение **Ushi** используется ежедневно и стабильно. Все изменения, описанные в этом брифе, **не должны касаться текущей сборки**, пока новая модель не отлажена.

**Решение:** создаём параллельную сборку **UshiNext** — отдельное приложение с другим bundle id и Application Support, устанавливается рядом с текущим Ushi. Когда UshiNext стабилизируется и полностью покрывает сценарий — переименуем в Ushi, старый удалим.

**Почему именно `UshiNext`:**

- `UshiDev` намекал бы на «временное/отладочное» — а это будущий основной продукт, не дев-ветка. Психологически легче ежедневно пользоваться приложением, которое называется «следующая версия», а не «дев».
- `Ushi 2` — финальное имя для релиза, когда замена реально состоится. Сейчас рано: ещё непонятно, доедет ли модель Проектов в текущем виде, не хочется жечь «версию 2» на промежуточную сборку.
- `UshiNext` честно описывает статус: параллельная сборка, куда переезжаем. Когда стабилизируется — переименуем в `Ushi`, и `Next` исчезнет естественно.

**Параметры новой сборки:**

| Параметр | Значение |
|---|---|
| Product Name | `UshiNext` |
| Display Name | `Ushi Next` |
| Bundle Identifier | `com.icemac.UshiNext` |
| Application Support | `~/Library/Application Support/UshiNext/` |
| UserDefaults suite | `com.icemac.UshiNext` |
| Иконка menu bar | базовая `MenuBarWaveform` + точка в углу для визуального отличия |

**Как делается:**

1. Дубликат всей папки `ushi/` → `ushi-next/`.
2. В `ushi-next/ushi.xcodeproj` меняем: Product Name, Bundle Identifier, Display Name.
3. Все пути к Application Support идут через одну константу `AppContainer.name` (создать, если её ещё нет) — меняем её на `"UshiNext"`. Аналогично для UserDefaults suite.
4. Иконка menu bar — duplicate `MenuBarWaveform.imageset`, добавить точку в углу (PDF/SVG), подключить в asset catalog.
5. Проверить независимый запуск: обе сборки видны в `/Applications`, у каждой свой menu bar иконка, базы данных и записи не пересекаются.

После того как UshiNext стабильна и устраивает — мигрируем (см. раздел 12).

## 1. Цель и проблема

**Проблема сегодня:**

- Все записи (психолог, лекции, встречи с коллегами, пет-проекты) попадают в один общий список без разделения.
- Источник записи (только микрофон / системный звук + микрофон / экран) — глобальный, надо помнить переключать перед каждой записью.
- Физически все файлы лежат в одной директории — это превращается в свалку, неудобно для бэкапа и приватности.

**Что хотим:**

- Разделять записи по контекстам (Проектам).
- У каждого Проекта — свой пресет источника, который запоминается и применяется автоматически.
- Возможность хранить файлы Проекта в произвольном месте на диске (Documents, Рабочий стол), а не только в недрах приложения.
- Не обязывать выбирать Проект перед каждой записью — быстрый старт без Проекта остаётся главным сценарием.

## 2. Терминология

| Термин | Что значит |
|---|---|
| **Проект** | Контейнер для записей одного контекста. Имеет имя, директорию, пресет источника по умолчанию. |
| **Запись** | Один файл: аудио (`.m4a`) или видео+звук (`.mov`). Принадлежит одному Проекту или лежит вне Проектов («Записи»). |
| **Пресет источника** | Конфигурация записи: что писать (микрофон / системный звук / экран). |
| **Записи** (orphan-секция) | Раздел sidebar для записей, не привязанных к Проекту. Заменяет термин «Без проекта». |
| **Inbox-старт** | Запись с главной кнопки — попадает в «Записи». |
| **Project-старт** | Запись через иконку ⏺ у Проекта в sidebar — попадает в этот Проект. |

В UI слово «Проект» используется везде; «Папка» не используем (путается с file-system).

## 3. Концептуальная модель

### Главные принципы

1. **Проект помнит, как в него записывают.** При каждой записи в Проект его «последний использованный пресет» обновляется. Следующая запись стартует с ним. Это даёт sticky-поведение без диалогов и настроек.

2. **Запись хранит immutable snapshot пресета.** При создании записи в её метаданных навсегда фиксируется: какой источник был использован, какой Проект, когда. Если потом пресет Проекта изменится — старые записи не «перекрасятся» задним числом.

3. **Главный сценарий — быстрый старт без Проекта.** Главная кнопка «Начать запись» всегда стартует в «Записи» (orphan), независимо от того, что было в прошлый раз. Это закрывает кейс «не до выбора, нужно срочно нажать».

4. **Старт внутрь Проекта — отдельный путь через sidebar.** У каждого Проекта в sidebar есть иконка ⏺ — клик стартует запись прямо в этот Проект с его пресетом.

5. **Перенос записи между Проектами — лёгкий.** Ошибся — открыл контекстное меню записи → «Переместить в → Лекции», 2 клика.

## 4. Модель данных

### Project

```swift
struct Project: Identifiable, Codable {
    let id: UUID
    var name: String                  // «Психолог»
    var icon: String?                 // SF Symbol name, optional
    var colorHex: String?             // акцентный цвет в sidebar, optional

    // Где физически живут файлы
    var storage: ProjectStorage

    // Дефолт-пресет для следующей записи в этот проект
    var lastUsedPreset: RecordingPreset

    var isPinned: Bool
    var createdAt: Date
    var updatedAt: Date
}

enum ProjectStorage: Codable {
    case managed                       // Application Support/UshiNext/Projects/{id}/
    case external(bookmark: Data,      // security-scoped bookmark
                  displayPath: String) // «~/Documents/Психолог»
}

enum RecordingPreset: String, Codable {
    case micOnly                       // только микрофон
    case systemAndMic                  // системный звук + микрофон
    case screen                        // экран + системный звук (+ микрофон если включён)
}
```

### Recording

```swift
struct Recording: Identifiable, Codable {
    let id: UUID
    var projectId: UUID?               // nil → лежит в «Записи»

    var title: String                  // авто-имя или вручную
    var fileURL: URL                   // через bookmark, если external
    var fileSize: Int64
    var duration: TimeInterval
    var createdAt: Date

    // Immutable snapshot: как меня записали
    var presetSnapshot: RecordingPreset
    var hasMicrophone: Bool
    var hasSystemAudio: Bool
    var hasScreen: Bool

    // Auto-имя
    var titleSource: TitleSource        // .auto / .manual / .fallback
    var transcriptStatus: TranscriptStatus  // .pending / .done / .failed
}

enum TitleSource: String, Codable {
    case auto                          // первое предложение из whisper
    case manual                        // юзер переименовал
    case fallback                      // {Project} · {дата} — если whisper не сработал
}
```

### Где хранится модель

- SQLite через GRDB или Core Data — `~/Library/Application Support/UshiNext/store.sqlite`.
- Bookmarks (security-scoped) — внутри `ProjectStorage.external`, хранятся в той же БД.
- Аудио/видео файлы — на диске (см. ниже).

## 5. Физический слой

### Managed-Проект (default)

Создаётся в `~/Library/Application Support/UshiNext/Projects/{project_id}/recordings/`.

Плюсы:
- Приложение полностью контролирует структуру.
- Move между Managed-Проектами — мгновенный (один том).
- Не требует доступа к произвольным путям → проще sandbox.

Минусы:
- Файлы «спрятаны» от Finder.

### External-Проект

Юзер выбирает существующую папку (или создаёт новую) — например, `~/Documents/Психолог/`. Приложение получает security-scoped bookmark и сохраняет его в `ProjectStorage.external`.

Плюсы:
- Файлы видны в Finder.
- Можно подключить к iCloud Drive, Dropbox, бэкапу.
- Можно делиться с другими инструментами (Audacity, текстовый редактор).

Минусы и риски:
- Папку могут переименовать/удалить вне приложения — нужно gracefully обрабатывать (degraded state, попросить reconnect).
- Move между External (Documents) и External (Desktop) на разных томах — это копирование + удаление, может быть медленным и упасть. Показываем progress + честно сообщаем об ошибках.

### Создание Проекта — два варианта

В модалке создания:

1. **«Создать в Ushi» (default).** Юзер вводит только имя. Папка создаётся в managed-месте. Юзеру не показываем путь, потому что это деталь реализации.
2. **«Использовать существующую папку».** Открывается NSOpenPanel, юзер выбирает папку, получаем bookmark. Имя по умолчанию = имя папки, можно изменить.

### 6.2 Sidebar — аккардеон Проектов

- Каждый Проект — раскрываемая строка. По умолчанию **раскрыт**, показывает 5 последних записей.
- Справа на строке Проекта при hover: иконка **⏺** (быстро записать в этот Проект) и **⋯** (контекстное меню).
- «Показать больше» под списком → раскрывает все записи Проекта. При повторном клике — «Показать меньше».
- Сортировка Проектов:
  - Закреплённые сверху (с иконкой 📌).

### 6.3 Sidebar — секция «Записи»

- Идёт **под** секцией «Проекты».
- Заголовок: просто `── Записи ──`.
- Содержит только orphan-записи (без `projectId`).
- Поведение раскрытия — то же: 5 последних + «Показать больше».
- Главный entry point новых юзеров: пока Проектов нет, всё попадает сюда.

Большая кнопка сверху sidebar. Поведение:

## 7. Поведение

### 7.1 Старт записи — 3 пути

Концептуально путей всего два (orphan-старт и project-старт), но входных точек три. У приложения есть **один глобальный пресет** `app.lastUsedPreset` — он же отражается в menu bar; отдельной menu-bar-настройки нет.

1. **Главная кнопка в окне** (или эквивалент в menu bar «Начать запись») → пишет в «Записи», использует `app.lastUsedPreset`. После успешной записи обновляет `app.lastUsedPreset`.
2. **Иконка ⏺ у Проекта в sidebar** (или menu bar «Записать в Проект → …») → пишет в выбранный Проект, использует `project.lastUsedPreset`. После успешной записи обновляет `project.lastUsedPreset`.
3. **Hero-стейт в окне** — то же, что путь 1, но с возможностью переключить пресет/Проект через chip-ы перед стартом. Если выбран Проект — берётся его пресет; если меняется пресет — он становится новым `lastUsedPreset` для того контекста, в который пошла запись.

Менюбарное подменю «Источник» — это просто способ поменять `app.lastUsedPreset`, не отдельный «менюбарный» пресет.

### 7.2 Сохранение пресета

После успешной записи:

- Если `projectId != nil` → `project.lastUsedPreset` обновляется на тот, что использовался.
- Если `projectId == nil` → `app.lastUsedPreset` обновляется.
- В саму запись (`presetSnapshot`) пишется immutable копия.

### 7.3 Авто-имя через Whisper

1. После остановки записи — файл сразу сохраняется с fallback-именем (`{Проект или «Запись»} · {дата время}`).
2. В фоне запускается транскрипция первых 30 секунд через whisper-cli.
3. Из транскрипта берётся первое полное предложение (~5-12 слов), это становится `title`. `titleSource = .auto`.
4. Если whisper не сработал (тишина, ошибка) — остаётся fallback, `titleSource = .fallback`.
5. Если юзер переименовал руками — `titleSource = .manual`, авто-имя больше не накладывается.

### 7.4 Move to

- **Managed → Managed:** `FileManager.moveItem` — мгновенно. Обновить `fileURL` и `projectId` в БД.
- **Managed → External:** копирование (с прогрессом, если > 50 МБ), удаление оригинала после успеха.
- **External → External (тот же том):** мгновенно.
- **External → External (разные тома):** копирование + удаление, с прогрессом.
- **Ошибки:** не удалять оригинал, пока копия не подтверждена. Если упало — запись остаётся в исходном Проекте.

### 7.5 Поиск

- Один глобальный поиск, кнопка/поле сверху sidebar.
- Ищет по: `title`, по транскрипту, по имени Проекта.
- Результаты — список записей, у каждой badge с Проектом (или «Без проекта»).
- Открытие результата → подсветить в sidebar (раскрыть нужный Проект) и показать в деталях.

### 7.6 External-Проект в degraded state

Если bookmark не резолвится (папка переименована или удалена):

- В sidebar Проект показывается с иконкой ⚠ и неактивным цветом.
- При попытке записи — модалка «Папка проекта недоступна. Подключить заново» с NSOpenPanel.
- Существующие записи Проекта не теряются — они остаются в БД с пометкой «файл не найден», в деталях видно «Файл недоступен, восстановите папку».

```
│ ViewModel (@Observable)              │  ← заменяемо вместе с View
│  - SidebarViewModel                  │
│  - RecordingDetailViewModel          │
│  - CreateProjectViewModel            │
├──────────────────────────────────────┤
│ Store (бизнес-логика)                │  ← стабильное ядро
│  - ProjectStore                      │
│  - RecordingsStore (расширяется)     │
│  - RecordingController (есть)        │
├──────────────────────────────────────┤
│ Persistence + FS                     │  ← стабильное ядро
│  - GRDB (SQLite) wrapper             │

└──────────────────────────────────────┘

**Persistence — GRDB**, не Core Data. Почему: явные миграции (видны в коде, можно тестировать), value-типы вместо `NSManagedObject` (играют с `@Observable`), нет threading-боли Core Data. Цена — нужно писать SQL/QueryInterface руками, но схема у нас маленькая (2-3 таблицы), это норм.
```

- Store/Persistence/FS — не знают про SwiftUI. Их API — методы вида `addProject(name:storage:preset:)`, `move(recording:to:)`, `delete(project:withFiles:)`.
- ViewModel — тонкая прокладка: подписывается на Store, форматирует данные для View, отправляет действия в Store.
- View — глупый, рендерит ViewModel.

Если завтра захочется three-pane / вкладки / iOS-версия — переписываем только верхние два слоя. Store и Persistence остаются.

### Тесты

- Store покрываем unit-тестами: создание проекта, перенос записи, удаление, snapshot пресета.
- BookmarkResolver и FileMover — отдельные тесты, потому что там IO-ошибки и edge cases.

## 9. Чего НЕ делаем сейчас (roadmap v2+)

- **Локальный LLM для умных названий и саммари записей.** Очень хотим, но это +неделя работы, +вес модели на диск, +память. Делаем после того, как базовая модель Проектов работает. Это станет ключевой продаваемой фичей, надо заложить место в архитектуре (отдельный сервис `Summarizer`, в который сейчас встроена whisper-based эвристика, потом дополнится LLM).
- **Шаблоны Проектов** («Создать из шаблона: Терапия / Лекции / Встречи»).
- **Глобальные хоткеи** (⌘⇧R для старт/стоп).
- **Auto-выбор Проекта** по календарю / приложению на переднем плане.
- **Вложенные Проекты.**
- **Шаринг Проекта между устройствами / iCloud-синхронизация.**
- **Аудит изменений пресетов.**

## 11. Миграция из текущего Ushi

Один-в-один импорт, без потерь:

1. UshiNext при первом запуске обнаруживает старую базу в `~/Library/Application Support/ushi/`.
2. Показывает экран онбординга: «Найдены записи из Ushi. Импортировать?»
3. При согласии: копирует (не перемещает) все файлы и метаданные в UshiNext. `projectId = nil` для всех. Старый Ushi остаётся целым.
4. Юзер сам растаскивает записи по Проектам через Move to (или не растаскивает — это норм).

После того как юзер уверен, что всё перенесено и UshiNext полностью заменяет старое — старый Ushi удаляется руками.

## 13. Зафиксированные технические решения

Закрыто до начала кода, не пересматривать без причины:

- **Persistence — GRDB** (см. §8).
- **Sandbox — нет.** UshiNext не sandboxed, App Store как канал доставки не рассматривается. Bookmarks используем не из-за sandbox-требований, а для устойчивости при переименовании/перемещении внешних папок.
- **Один глобальный `app.lastUsedPreset`** + `project.lastUsedPreset` на каждый Проект. Menu bar не имеет собственного пресета — рендерит и правит `app.lastUsedPreset` (см. §6.9, §7.1).
- **Whisper уже встроен** в текущий Ushi (`TranscriptionService`, `whisper.cpp` в vendor, `ModelManager`). Авто-имя в Phase 4 — это новое потребление готового сервиса, не новая зависимость.
- **Override-флоу и privacy-warnings отменены.** Последний использованный пресет молча выигрывает. Если ошибся проектом — Move to решает за 2 клика.

## 14. Что не входит в этот бриф и решается на реализации

- Точная вёрстка hero-экрана (нужны мокапы перед Phase 2).
- Точные шорткаты клавиатуры (есть в roadmap v2 как глобальные хоткеи).
- Выбор между `RecordingPreset` как `enum` vs более гранулярными флагами (`hasMic`, `hasSystem`, `hasScreen`) — решится при написании модели в Phase 1.

Эти вещи не блокируют старт.
